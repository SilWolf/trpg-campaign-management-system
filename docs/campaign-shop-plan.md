# 戰役內商店：開發規劃

## 目標

在每個戰役中提供一個或多個由 DM 管理的商店。DM 可設定店名、背景圖片、商品售價、庫存及是否需要審查；玩家選擇自己的角色與付款錢包後購買。商店商品來自鍛造工坊，購買及審查請求留下戰役成員可公開閱覽的紀錄。

本功能沿用既有戰役成員、角色 ACL、雙錢包、背包物品與鍛造工坊，不建立全域商店或全域庫存，也不把 `camp-chest` 當成可購物角色。

## 已確認規則

| 項目 | 規則 |
| --- | --- |
| 商店數量與管理 | 每個戰役可有多家商店；只有該戰役 DM 可建立、修改及停用商店與商品。 |
| 商店圖片 | 以圖片網址設定，不包含 Supabase Storage 上傳。 |
| 購物角色 | 玩家只能選擇自己在該戰役擁有的角色；`camp-chest` 不可作為購物角色。 |
| 付款權限 | 公開錢包及私人錢包分開驗證。玩家只能選擇具有對應修改權 (`2`) 的錢包；DM 可按既有 DM 權限規則操作。 |
| 商品來源 | 可從鍛造工坊匯入，包含規則書目錄物品、自己的鍛造物品及其他使用者分享的鍛造物品。匯入後保留商品快照，不依賴來源項目持續存在。 |
| 批次匯入 | 一行一項，欄位以 `|` 分隔：`物品名稱|單價（gp）|庫存數量`。 |
| 付款審查 | 需要審查的請求建立時先保留庫存、不扣款；DM 核准時才扣款並交付物品，拒絕或玩家取消時釋放保留庫存。 |
| 售價及找零 | 售價以 gp 表示。按 D&D 幣值換算並只從玩家選定的錢包扣款；在該錢包內找零，不跨公開／私人錢包。 |
| 購買數量 | 不設額外的每筆購買數量上限；不得超過可用庫存及玩家該錢包的可支付金額。 |
| 公開紀錄 | 戰役成員可查看角色、品項、數量、單價、狀態及時間；不公開付款錢包種類或餘額。 |

## 範圍與非目標

### 第一階段包含

- 商店列表、商店管理及商店商品管理。
- 從工坊搜尋／選擇物品匯入商店，並由 DM 編輯售價、庫存及是否需要審查。
- 純文字批次匯入與逐行驗證預覽。
- 玩家選角、選擇公開或私人錢包、設定購買數量及送出購買／審查請求。
- DM 檢視待審請求並核准或拒絕。
- 公開商店購買紀錄及請求狀態。
- 遠端 Supabase 儲存、RLS、Realtime 和離線／訪客模式退避。

### 第一階段不包含

- 交易稅、折扣、議價、商店營業時間或按角色等級限制。
- 退貨、退款、已完成購買的撤銷或跨錢包找零。
- 商店圖片檔案上傳、商品評論或玩家寄售。
- camp-chest 購物或從戰役背包直接回售商品。
- 為交易使用前端多次寫入來模擬原子操作。

## 使用流程

### DM 建立與管理商店

1. 從戰役頁面進入商店區，建立商店並填寫名稱及背景圖片網址。
2. 從鍛造工坊搜尋目錄及分享物品，或選擇自己的鍛造樣板，匯入一項或多項商品。
3. 為每項商品設定 gp 售價、可用庫存及是否需要 DM 審查。
4. 可修改商店名稱、圖片、商品設定及庫存，或停用商店／商品。停用不刪除歷史訂單。
5. 在審查頁檢視待處理請求並核准或拒絕；可見角色、商品、數量及總價。

### 玩家購買

1. 開啟戰役商店並選擇一家啟用中的商店。
2. 選擇自己擁有的戰役角色；只有對應公開或私人錢包修改權為 `2` 的付款方式可用。
3. 選擇商品、數量及付款錢包。UI 顯示總價和所選錢包可支付狀態。
4. 不需審查的購買在確認後立即扣款、減少庫存並將物品放入角色公開背包。
5. 需要審查的購買建立待審請求並保留庫存，不扣款。待審期間玩家可取消；取消後釋放庫存。
6. DM 核准時，以當下資料重新驗證請求、錢包餘額及角色／商店狀態，再扣款、完成庫存扣減並交付物品；若無法完成，整筆核准失敗且請求維持待審。拒絕時更新狀態並釋放庫存。
7. 戰役成員可在商店紀錄查看已完成交易及請求狀態，不會看到付款錢包種類或金額餘額。

## 資料與邊界設計

實作前需依目前 Supabase schema 核對現有欄位及 constraint；建議新增獨立增量 migration，不修改既有角色、物品或錢包欄位。

### 建議資料表

#### `campaign_shops`

商店基本資料：

- `id text`：商店識別碼。
- `campaign_id text`：所屬戰役，外鍵依現有規則級聯刪除。
- `name text`：商店名稱。
- `background_image_url text`：可為空的圖片網址。
- `is_active boolean`：停用後不可購買，歷史資料保留。
- `created_at`、`updated_at`。

所有查詢與修改均以 `campaign_id` 限定；不得依固定 campaign ID 或預設商店特例授權。

#### `campaign_shop_items`

戰役商店中的商品設定：

- `id text`、`campaign_id text`、`shop_id text`。
- `item_snapshot jsonb`：匯入時的物品定義快照，包括名稱、分類、稀有度、圖示、重量、物品描述及鍛造工坊可用的其他定義欄位。不含角色擁有者、目前充能、裝備狀態等實例狀態。
- `source_type text` 及 `source_id text`：記錄來源類型／識別碼供 DM 追溯；不建立對工坊資料的外鍵。
- `unit_price_gp numeric`：大於零的單價，明確限制精度及最大值。
- `stock_available integer`：可供新購買的數量。
- `stock_reserved integer`：待審請求已保留的數量。
- `requires_approval boolean`、`is_active boolean`、時間欄位。

匯入時複製物品定義，不沿用來源資料列 ID 作為背包物品 ID。來源樣板日後刪除或修改不影響已建立的商店商品；已完成交易另保存當時的商品與售價快照。

#### `campaign_shop_orders`

購買及審查的公開紀錄：

- `id text`、`campaign_id text`、`shop_id text`、`shop_item_id text`。
- `buyer_user_id uuid`：登入者帳號。
- `character_id text`：購買角色。
- `item_snapshot jsonb`、`shop_name_snapshot text`、`unit_price_gp numeric`、`quantity integer`、`total_price_gp numeric`：鎖定交易發生時的公開紀錄快照。
- `status text`：限制為 `completed`、`pending`、`rejected`、`cancelled`。
- `requires_approval boolean`、`created_at`、`updated_at`、`reviewed_by uuid`、`reviewed_at`。

不在公開紀錄中儲存付款錢包種類、錢包餘額或私人貨幣明細。DM 審查時以該訂單綁定的角色及伺服器端驗證資料執行付款，不接受前端變更已建立訂單的角色、品項、數量或價格。

### 狀態與庫存規則

| 操作 | 訂單狀態 | 可用庫存 | 保留庫存 | 扣款／交付 |
| --- | --- | --- | --- | --- |
| 直接購買成功 | `completed` | 減少購買數量 | 不變 | 同一交易內扣款並交付 |
| 建立待審請求 | `pending` | 減少購買數量 | 增加購買數量 | 不扣款、不交付 |
| 核准待審請求 | `completed` | 不變 | 減少購買數量 | 同一交易內扣款並交付 |
| 拒絕待審請求 | `rejected` | 增加購買數量 | 減少購買數量 | 不扣款、不交付 |
| 玩家取消待審請求 | `cancelled` | 增加購買數量 | 減少購買數量 | 不扣款、不交付 |

DM 調整庫存時只編輯可用數量，且不得使庫存為負數。已保留的數量不得被刪除或再次出售；停用商店／商品不會自動取消既有待審請求，DM 仍須明確核准或拒絕。

## 貨幣與交易一致性

- 使用 D&D 換算比率：`1 pp = 10 gp`、`1 gp = 10 sp`、`1 ep = 5 sp`、`1 sp = 10 cp`。以整數 cp 換算售價與錢包價值，並定義售價允許的最大精度，避免浮點誤差。
- 只讀取及修改訂單指定角色的指定錢包（`currencies` 或 `private_currencies`）。若在該錢包內支付後需要找零，只能在同一個錢包中找零；另一個錢包的貨幣不得合併計算。
- 交易完成後，把商品快照轉成新的 `inventory_items` 實例，`owner_id` 設為購物角色 ID、`campaign_id` 設為當前戰役、`quantity` 設為購買數量、`is_private = false`。依現有物品初始化規則設定裝備、鑑定及充能狀態。
- 不依賴 `useCampaignSync` 的 optimistic 多列寫入完成購買。錢包、庫存、訂單狀態及背包物品必須由單一 PostgreSQL 交易 RPC 原子修改；任何一步失敗都回滾整筆操作。
- 直接購買、建立待審請求、核准、拒絕及取消各使用具明確授權檢查的資料庫函式。使用資料列鎖或等效併發控制，避免多人同時購買超賣、重複扣款或同一請求重複核准。
- 核准時要重新檢查可用餘額。建立待審請求不凍結玩家貨幣；若玩家在等待期間花掉所選錢包中的貨幣，核准應失敗並保留待審狀態，DM 可請玩家補足或拒絕。

## 權限、安全與同步

### RLS 與資料庫授權

- 只有戰役成員可讀取該戰役啟用中的商店、商品及公開訂單紀錄；非成員不能透過 REST 或 Realtime 讀取其他戰役資料。
- 只有 DM 可建立／修改商店、商品價格與庫存，並審查訂單。一般玩家只能建立自己的訂單、取消自己的待審請求；不可直接寫入 `completed` 或自行變更交易快照。
- 交易 RPC 必須以 `auth.uid()` 驗證登入者、campaign 成員、DM 身分、角色所有權及錢包 ACL；不可信任前端傳入的價格、付款餘額或審查者 ID。
- `campaign_id`、角色與使用者的型別依既有 schema：campaign／character ID 與 `characters.user_id` 為 `text`，帳號及 ACL 使用者 ID 為 `uuid`。比較角色擁有人與登入者時使用 `auth.uid()::text`；不要把 `camp-chest` 或 `guest` 當 UUID。
- 購物角色必須屬於當前戰役且由登入者擁有。私人錢包付款須驗證 `private_wallet_access = 2`，公開錢包付款須驗證 `public_wallet_access = 2`。若授權資料需在 RLS policy 中輔助查詢，使用符合專案慣例的 `SECURITY DEFINER` helper，避免 policy 直接查詢自身表格造成無限遞迴。
- 交易函式採固定 `search_path` 並明確限制執行權限；遵循既有手動部署及 migration history 檢核流程。不連接或修改未經維護者確認的 Supabase 專案。

### Realtime 與離線模式

- 遠端模式由 Supabase 為商店、商品與訂單提供唯一資料來源，Realtime 訂閱以當前 `campaign_id` 篩選。
- 訂單狀態與庫存異動需使 DM 與玩家畫面更新；交易結果以 RPC 回傳及資料庫狀態為準，不把前端 optimistic 更新視為成功。
- 未設定 Supabase 或訪客模式需清楚顯示商店雲端功能不可用；不得將離線建立的商店或購買請求誤報為已同步／已完成。若選擇提供本機展示，可使用明確標示為本機的模擬資料，不可冒充遠端交易。
- Realtime 只負責通知，不取代 RPC 授權與 RLS。

## UI 與路由建議

- 在 `/campaigns/$campaignId/` 新增戰役商店入口，玩家和 DM 共用瀏覽介面；DM 額外看到管理與審查操作。
- 建議以巢狀商店區呈現列表／商店詳情、管理分頁及公開紀錄。路由由 TanStack Router 檔案自動產生，不手動修改 `src/routeTree.gen.ts`。
- 玩家購物介面先選角色，再以該角色的 ACL 過濾可用付款方式；沒有任何錢包修改權時，顯示明確原因並停用購買。
- 購物確認前顯示數量、gp 單價、總價、庫存及是否需審查。對需審查商品明確說明「送出後保留庫存，核准前不扣款」。
- DM 管理介面需清楚區分可用庫存與待審保留數量；可查看各筆請求並處理，不可因商店停用而遺失歷史紀錄。
- 背景圖片網址須驗證格式並在失效時回退至既有深色奇幻背景；圖片只作展示，不得由伺服器任意抓取網址內容。
- 批次匯入使用多行文字區，每行格式 `名稱|單價|庫存`。忽略空白行；欄位數量錯誤、空名稱、非正數售價、負數／非整數庫存、超出精度或包含未跳脫 `|` 的名稱都要標出行號。預覽全部通過後才允許一次匯入，錯誤不得靜默略過。

4. [ ] 以兩個以上帳號在隔離 Supabase 專案驗證權限、RLS、Realtime 及併發交易，再由維護者手動部署。

**目前實作：** 基礎 migration 為 [`20261026000000_campaign_shops.sql`](../supabase/migrations/20261026000000_campaign_shops.sql)，整車結帳增量 migration 為 [`20261027000000_campaign_shop_cart_checkout.sql`](../supabase/migrations/20261027000000_campaign_shop_cart_checkout.sql)。原始 schema 只支援單項 RPC 結帳；新增 `checkout_id` 與 `checkout_campaign_shop_cart` 後，多項商品會在單一 PostgreSQL 交易內一併扣款／交付，或在包含任一審查商品時全數建立為同組待審記錄。核准、拒絕與取消也是整組處理。交易函式以資料列鎖保護商品庫存、訂單及角色錢包；價格以最多兩位小數的 gp 儲存並換算為整數 cp，找零只寫回訂單綁定的同一錢包。待審請求先保留庫存；其付款錢包種類只存於一般使用者不可讀寫的輔助表，不列入公開訂單欄位。付款不足或任何交付失敗會令 PostgreSQL 整筆交易回滾。

**尚未驗證／不可宣稱完成：** 此環境沒有 `psql` 或 Supabase CLI，本次未套用 migration，也未連線任何 Supabase 專案。兩帳號 RLS、Realtime、併發超賣及失敗回滾驗收仍待維護者在確認過的隔離專案執行；完成前不可視為已部署或通過資料庫驗收。

**完成條件：** RLS 無遞迴；未授權的直接寫入遭拒；購買與庫存／錢包更新完整原子化；同一庫存不足時併發請求不會超賣。上述條件中的真實資料庫驗收目前仍待執行。

## 驗收清單

- DM 可建立多家商店，修改名稱與圖片網址，停用後仍可查看舊訂單。
- DM 可從官方目錄、自己的樣板及他人分享樣板匯入；可調整售價、庫存與審查要求。
- 每行 `名稱|單價|庫存` 都會獨立驗證；任一行錯誤時不會匯入部分資料。
- [x] 玩家不能以他人角色或 `camp-chest` 購物；公開／私人錢包各自要求對應修改權 `2`（前端過濾與交易 RPC 權限檢查；真實 RLS 待隔離環境驗收）。
- 付款換算只使用選定錢包的幣值，找零也只回到同一錢包；錢包不足時交易失敗且庫存、訂單、物品均不變。
- [x] 直接購買透過原子 RPC 扣款、扣減庫存、建立公開紀錄及加入角色公開背包；RPC 重複呼叫保護仍須資料庫驗收。
- [x] 待審請求透過 RPC 保留庫存但不扣款；核准才扣款並交付；拒絕／取消釋放保留庫存。
- 玩家等待審查期間餘額不足時，核准失敗且不扣款、不交付，請求仍可供 DM 處理。
- 多人同時競買最後庫存時不超賣；對同一請求重複核准不會重複扣款或交付。
- [x] 戰役成員可查閱公開紀錄；前端紀錄不暴露付款錢包種類及餘額。非成員讀取／Realtime 隔離尚待真實資料庫驗收。
- 刪除戰役時，只級聯清除所屬商店資料，不影響鍛造工坊來源項目或其他戰役。
- 離線／訪客操作不會顯示成功的遠端購買或建立待審請求。
