## 針對不同架構的具體建議

### 1. 如果你的專案已經整合 Supabase（首選推薦）

如果你的專案後端與資料庫已經在用 Supabase，**直接使用 Supabase Storage 是最省事的做法**。

- **為什麼選它**：你不需要另外申請帳號或管理第二套金鑰。可以直接利用 Supabase Auth 設定 Storage Bucket 的 RLS 權限（例如：「只有登入的使用者可以上傳圖片到自己的資料夾，且所有人皆可讀取」）。
- **前端實作小技巧**：由於標準免費版的即時圖片變形（Image Transformation）有限制，建議在 React 前端先使用 `browser-image-compression` 或 Canvas API 將圖片壓縮並轉為 `.webp` 格式後，再呼叫 `supabase.storage.from('bucket').upload()`，這樣能大幅節省那 1GB 的免費空間。

### 2. 如果你是純前端專案，且不想管後端簽章：選 Cloudinary

如果你不希望為了圖片上傳多寫一個 Serverless API 來簽發 Token，**Cloudinary 的 Unsigned Upload（無簽章上傳）** 是純 Vite 專案的好朋友。

- **為什麼選它**：在後台設定一個 Upload Preset（限制檔案大小、格式與目標資料夾），前端只需要用普通的 `fetch` 或 `axios` 發送 `FormData` 就能拿到圖片網址。拿到網址後，只要在 URL 中加上 `f_auto,q_auto,w_500`，就能自動以 WebP 格式與指定寬度載入。

### 3. 如果專案部署在 Vercel 且重度依賴圖片讀取：選 Cloudflare R2 / Vercel Blob

- 若圖片上傳後會被高頻率讀取（例如公開展示的卡片、道具圖鑑），傳統雲端服務的流量費（Bandwidth）很容易爆表。這時用 **Cloudflare R2** 搭配一個簡單的 Vercel API Route（或 Cloudflare Worker）來簽發 `Presigned URL` 讓前端直傳，能徹底免除流量焦慮。

## 一、 先算一筆容量與流量帳

我們先估算這批圖片對儲存空間與流量的實際消耗，你會發現容量其實非常輕量，真正的瓶頸在於**高頻率讀取的流量（Egress）與請求數**：

| 圖片類型                   | 數量預估 | 單張大小 (WebP)    | 總容量預估       | 讀寫特性                                             |
| -------------------------- | -------- | ------------------ | ---------------- | ---------------------------------------------------- |
| **預設道具圖鑑 (128x128)** | ~600 張  | 約 3 KB ~ 8 KB     | **~3.5 MB**      | 寫入一次、**極高頻率讀取**（背包格子、列表頻繁載入） |
| **預設道具圖鑑 (512x512)** | ~600 張  | 約 25 KB ~ 50 KB   | **~25 MB**       | 寫入一次、中頻率讀取（點擊檢視道具詳情時載入）       |
| **使用者大頭貼**           | 動態增長 | 約 15 KB (256x256) | **< 10 MB**      | 低頻率更新、高頻率讀取                               |
| **自訂道具圖示**           | 動態增長 | 約 5 KB ~ 40 KB    | **< 50 MB**      | 使用者或管理員動態上傳、中頻率讀取                   |
| **文章標題橫幅 (Banner)**  | 動態增長 | 約 100 KB ~ 250 KB | **視文章數而定** | 單張體積最大，若未壓縮容易吃掉大量空間與流量         |

全部加起來初期根本不到 **100 MB**，遠低於各大平台（包含 Supabase 1GB）的免費容量上限。但因為背包或圖鑑介面一次可能會載入幾十張 128x128 的小圖示，如果全部放同一個地方，很容易觸發第三方儲存服務的讀取次數限制或流量上限。

## 二、 最佳架構推薦：動靜分離（Vercel / CDN + Supabase Storage）

與其把所有圖片都塞進同一個雲端 Storage，最省錢、載入速度最快、且不用多維護一套第三方帳號的方案是 **「靜態圖鑑放前端託管 CDN，動態圖片放 Supabase Storage + 前端 Canvas 自動裁切轉 WebP」**：

### 1. 預設的 1,200 張道具圖鑑 ➔ 直接放專案 `public/`（或 Cloudflare R2）

這 600 組（128x128 與 512x512）預設圖示屬於「不會由一般使用者任意修改」的系統基礎資產，總大小才約 30MB。

- **做法**：直接放進 Vite 專案的 `public/icons/128/` 與 `public/icons/512/` 目錄下（例如 `public/icons/128/sword_01.webp`）。資料庫裡只需要存字串 `"sword_01.webp"`。
- **優勢**：

1. **完全不消耗雲端 Storage 額度**。
2. 部署在 Vercel 或 Netlify 時，會自動透過全球 Edge CDN 快取分發，玩家打開背包載入 100 個格子也是瞬間秒開。
3. 省去寫腳本把 1,200 張圖批次上傳到第三方服務的麻煩，還能直接跟著 Git 版控。

### 2. 大頭貼、自訂道具圖示、文章橫幅 ➔ 使用 **Supabase Storage**

這些屬於使用者在網頁操作時動態新增的內容（UGC），交給 **Supabase Storage** 處理最適合：

- **為什麼不選 Cloudinary？** 因為你的預設圖鑑已經切好 `128x128` 和 `512x512` 的 WebP 了，代表你很清楚需要的尺寸規格。與其為了動態圖片去串接 Cloudinary，不如在 React 前端上傳前，**直接用瀏覽器原生 `Canvas API` 在本地把使用者上傳的 PNG/JPG 自動轉成對應尺寸的 WebP** 再傳上去。
- **完美結合權限控制（RLS）**：你可以直接在 Supabase 建立兩個公開讀取（Public）的 Bucket（例如 `user-uploads` 與 `campaign-assets`），並設定 RLS 規則：「只有登入者可以上傳至自己的 UID 資料夾 (`auth.uid() = (storage.foldername(name))[1]`)」，安全性一步到位，完全不需要額外寫後端 API。

## 三、 前端上傳前的自動規格化策略（關鍵優化）

為了確保使用者不會直接把一張 5MB 的手機原圖或未壓縮 PNG 傳上你的儲存空間，建議在 React 寫一個共用的圖片處理工具函式，在上傳至 Storage 前自動在瀏覽器端完成轉換：

- **使用者大頭貼**：前端強制裁切/縮放為 `256x256` WebP（品質 0.85），單張不到 20KB。
- **自訂道具圖示**：使用者選取一張圖片後，前端在記憶體內**同時生成一張 `512x512` WebP 與一張 `128x128` WebP**，一次上傳兩張到 Storage 的 `/custom-icons/128/` 與 `/custom-icons/512/`。這樣自訂道具跟預設圖鑑的載入邏輯就能完全統一！
- **文章標題橫幅**：前端限制最大寬度為 `1200px` 或 `1600px`（等比例縮放或固定 16:9 裁切），轉為 WebP（品質 0.8），可將原本 4MB 的大圖壓縮到 120KB 左右。

### 資料庫欄位設計小技巧

為了讓前端元件（例如背包格子 `<ItemIcon/>`）能無縫顯示「預設道具」與「自訂道具」，資料表的 `icon_url` 欄位可以這樣設計：

- 若為預設圖示，存相對路徑：`default:sword_01.webp` ➔ 前端解析為 `/icons/128/sword_01.webp`
- 若為自訂上傳，存完整 URL 或 Storage 路徑：`[https://xxx.supabase.co/.../custom_01.webp](https://xxx.supabase.co/.../custom_01.webp)`

這樣規劃的話，你連半毛錢都不需要花，也不用引入額外的第三方上傳平台！
