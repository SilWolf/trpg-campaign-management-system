# UI 元件改造準備階段

本文件記錄改造前的頁面盤點、互動分類與 Playwright 基準測試策略。測試只驗證既有行為，不包含共用 UI 元件或業務邏輯改造。

## 路由與 Phase 1 範圍

| 使用者頁面 | 實際路由 | 現有內容與流程 |
| --- | --- | --- |
| 登入／註冊 | `/login` | Email、密碼、註冊模式切換、密碼顯示切換、訪客登入、錯誤與驗證提示 |
| Email 邀請註冊 | `/invite/{campaignId}` | 驗證邀請 session、設定密碼、確認密碼、接受戰役邀請；不發送 Email |
| 戰役列表／大廳 | `/` | 預設示範戰役、資料庫戰役列表、建立戰役、輸入邀請碼、登出、前往帳號設定 |
| 帳號設定 | `/settings/profile` | 顯示名稱與 Email 編輯、儲存、成功／錯誤回饋 |

盤點到的其他路由包括 `/campaigns/{campaignId}` 背包、`/campaigns/{campaignId}/settings` 戰役與角色設定，以及上述頁面的 layout／保護路由。這些不屬 Phase 1 E2E 範圍，應在 Phase 2、Phase 3 開始前各自補上基準測試。

## 改造前控制項盤點

對 `src/**/*.tsx` 中原生互動標籤做靜態計數（以 JSX 標籤出現次數計，不代表執行時數量）：

| 標籤 | 次數 | 分類 |
| --- | ---: | --- |
| `<button>` | 90 | 表單提交、頁面操作、彈窗控制與背包操作 |
| `<input>` | 41 | 登入／個人資料／戰役設定與道具角色編輯 |
| `<select>` | 12 | 角色權限與戰役設定選項 |
| `<textarea>` | 5 | 道具與角色描述／備註 |

主要互動可分為：

- **共通表單與操作**：登入／註冊、邀請密碼、個人資料、戰役名稱與邀請碼；有必填、Email 格式、密碼長度、兩次密碼相同等驗證。
- **複雜互動**：大廳建立／加入戰役對話框、角色與道具編輯對話框、權限分頁與選擇器；背包另使用 Vaul 行動版 Drawer。
- **產品專屬展示**：戰役卡片、背包格、物品提示、角色狀態列與貨幣面板，應保留各自視覺，不因共用元件導入而強制統一。
- **回饋狀態**：登入錯誤、註冊 Email 驗證提示、邀請失效／密碼不一致、建立或加入錯誤、個人資料成功／失敗。登入／邀請頁有 `role="alert"`；大廳與個人資料亦有錯誤與成功提示。
- **窄螢幕**：登入卡片採流動寬度；大廳標頭與操作區依斷點換行；帳號設定表單採單欄。準備階段以 375px viewport 對 Phase 1 四個頁面建立水平溢位回歸檢查。

## Playwright 測試資料與外部服務隔離

- `npm run test:e2e` 由 Playwright 啟動專用 Vite server，使用隔離的 `127.0.0.1:54321` 測試 Supabase URL，不讀取或連接任何正式 Supabase 專案。
- E2E fixture 以瀏覽器網路攔截提供固定 Auth、PostgREST 與 RPC 回應；每個測試使用新的 Browser context，不保存跨測試資料。
- 測試帳號與內容為固定虛構資料（`example.test`），沒有真實玩家資料或真實憑證。
- 註冊由 Auth 替身直接回覆驗證信提示，不寄送 Email；邀請接受使用受控 session 與 RPC 替身，不依賴信箱、OAuth 或外部服務。
- 若新增需要跨流程狀態的測試，應擴充 fixture 並確保每次測試可重複初始化；不可改用開發者 `.env.local` 內的服務。

## Phase 1 基準情境

`tests/e2e/phase-1-baseline.spec.ts` 覆蓋：

1. 註冊成功及 Email 驗證提示。
2. 登入必填欄位及認證失敗的使用者可見訊息。
3. 無效邀請連結提示。
4. 邀請註冊密碼確認及接受邀請。
5. 建立戰役後進入該戰役。
6. 使用邀請碼加入戰役。
7. 更新帳號資料並顯示成功狀態。
8. 375px 窄螢幕登入、邀請註冊、大廳與帳號設定頁的水平溢位檢查。

此基準只涵蓋改造前已存在且可由 UI 操作的流程。Email 寄送、真實 Auth 與持久化由隔離替身控制；測試並非 Supabase 部署或 RLS 的驗證。
