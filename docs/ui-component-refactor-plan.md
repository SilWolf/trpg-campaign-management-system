# UI 元件整理與逐步改造規劃

## 目標

逐步建立一致、易維護且符合《博德之門 3》暗黑奇幻風格的 UI 元件層，減少按鈕、輸入框與互動元件在各頁面重複撰寫樣式和行為的情況，同時保留背包等核心功能的客製化呈現。

本規劃採漸進遷移：既有頁面可持續運作，每一階段都能獨立驗收，不要求一次重寫整個前端。

## 建議方向

採用 **shadcn/ui 的元件組織方式與 Radix UI primitives 作為互動基礎，並以專案自己的共用元件封裝**。這不是直接套用一套完整的預設視覺主題；元件外觀仍由本專案的 Tailwind CSS 樣式與設計規則負責。

選擇此方向的原因：

- 現有前端已使用 Tailwind CSS v4、React、TypeScript 與 Lucide React，概念與工作方式相容。
- 可逐個引入元件實作，不必先遷移全站，也不會被固定的商用元件主題綁住。
- 對 Dialog、Dropdown、Tabs 等需要焦點管理、鍵盤操作與無障礙行為的元件，可使用成熟的 primitives，避免自行重造互動邏輯。
- 可保留專案的琥珀金、秘法紫、翠綠、青色與危險紅色語意。

### 工具與依賴原則

- shadcn/ui 是可複製並修改的元件程式碼組織方式，不是必須整包安裝的執行期 UI 套件。只引入確實使用的元件與其 primitives 依賴。
- 導入前先驗證 shadcn/ui CLI 與 Radix 元件在目前 Tailwind CSS v4、Vite、React 19 和 TypeScript 設定下的相容性。
- 保留現有 Lucide React 圖示。
- 保留 Vaul 作為行動版 Drawer 的基礎；不要同時再引入功能重疊的 Drawer 套件。
- 暫不導入 MUI、Ant Design 等帶有大型預設視覺系統的元件庫，以免大量覆寫樣式並削弱產品風格。
- 不以「所有 JSX 都必須改成共用元件」為目標；純展示且高度特殊的元件可維持專用實作。

## 設計與元件原則

### 視覺語意

共用元件應使用一致的深色基底與邊框規則，並依用途使用語意色：

| 語意 | 建議色系 | 例子 |
| --- | --- | --- |
| 一般操作、公開項目 | 琥珀金 | 主要按鈕、公開背包 |
| DM 專屬、魔法資訊 | 秘法紫 | DM 管理入口、魔法詞條 |
| 私人與安全狀態 | 翠綠 | 私人暗袋、安全提示 |
| 營地儲物箱 | 青色 | 營地儲物箱專屬標記 |
| 危險或不可逆操作 | 深紅 | 刪除、移除角色、解散戰役 |
| 中性操作 | 石色 | 次要按鈕、一般容器 |

字體與既有產品規範一致：標題使用 serif 粗體；數值、重量和貨幣使用等寬字體。

### 共用元件範圍

先建立能涵蓋常見使用情境的薄元件層：

- `Button`：variant、size、disabled、loading、圖示與危險操作樣式。
- `Input`、`Textarea`：標籤、錯誤、說明文字、disabled 和焦點狀態。
- `Select`、`Checkbox`、`Switch`：統一表單外觀與標籤關聯。
- `Badge`、`Alert`：狀態與提示語意。
- `Dialog`、`DropdownMenu`、`Tabs`：在有實際遷移需求時引入 accessible primitive。
- `FormField`：只有在重複模式已清楚時再抽取，避免過早建立表單抽象。

元件 API 使用明確的 TypeScript 型別，並保留必要的原生屬性、`ref` 與 `className` 擴充能力；避免使用 `any`、過度泛型或讓每個呼叫端都能覆寫完整設計規則的 API。

## 改造步驟

### 準備階段：盤點、Playwright 基礎設施與基準測試

1. 盤點各路由和元件中的原生 `<button>`、`<input>`、`<select>`、`<textarea>` 及自製互動元件，並確認各指定頁面的實際路由。
2. 分類共通表單／操作、複雜互動元件與產品專屬展示元件；記錄主要操作、錯誤狀態及窄螢幕版面。
3. 引入 Playwright，建立 E2E 設定、測試指令和最小可維護的測試目錄結構；設定本機開發伺服器啟動方式。
4. 決定可重複使用的測試登入與資料策略。優先使用隔離的測試環境或可重置的 fixture，不使用真實玩家資料，不依賴真實 Email 寄送或外部信箱收件。
5. 先為 Phase 1 涵蓋的頁面建立改造前基準 E2E 測試；若流程涉及外部 Email／OAuth 等外部服務，透過測試環境或受控替身驗證應用程式可控的流程。
6. 確認 Playwright 與目前 Vite、React、TypeScript 設定相容；避免在建立測試基礎設施時改動業務邏輯、Supabase Schema、RLS 或權限規則。

**完成條件：** Playwright 測試能在本機穩定執行；測試資料可隔離與重複建立；Phase 1 基準流程已記錄，並能在 UI 遷移前通過。

### 共用元件基礎建置

1. 在既有樣式入口整理共用語意樣式：顏色、邊框、焦點環、圓角、尺寸與層級。
2. 建立建議位置 `src/components/ui/`，集中放置可重用的低階 UI 元件。
3. 先實作 `Button`、`Input`、`Textarea`、`Badge`，並為每一種 variant 明確定義用途。
4. 確保按鈕預設 `type="button"`，避免表單內未指定 type 的按鈕意外送出。
5. 確保元件具備可見的 `focus-visible` 狀態、合理的 disabled 行為及可讀的標籤／錯誤關聯。
6. 視需要建立受控的元件展示頁或 Storybook；若不引入展示工具，則在每個 Phase 的頁面驗收中檢查元件狀態。

**完成條件：** 共用元件 API 清楚且經頁面驗證；鍵盤焦點清楚；既有頁面仍可正常建置。

### Phase 1：登入、註冊、Email 邀請註冊、戰役列表、帳號設定

**範圍**

- 登入頁。
- 註冊頁。
- Email 邀請註冊頁。
- 戰役列表頁。
- 帳號設定頁。

**執行步驟**

1. 先完成上述頁面的 Playwright 基準測試，涵蓋主要成功流程、必要欄位驗證與使用者可見的錯誤／成功回饋。
2. 建立或調整共用表單、按鈕、提示與狀態元件。
3. 逐頁遷移上述範圍內的共通 UI；保留頁面資料流、驗證、Auth 呼叫、戰役加入與建立行為。
4. 每完成一頁，執行對應 E2E 測試，並檢查鍵盤操作、focus 狀態及窄螢幕版面。

**完成條件：** 指定頁面的主要流程與回饋有自動化覆蓋；Playwright 測試通過；不改變登入、註冊、邀請接受、戰役建立／加入及帳號資料更新的既有行為。

### Phase 2：Campaign 設定頁

**範圍**

- Campaign 常規設定與成員配額。
- Email 邀請管理入口。
- 角色設定、角色轉移與刪除。
- 角色權限矩陣及相關提示。

**執行步驟**

1. 在本階段 UI 遷移前，先補齊 Campaign 設定頁的 Playwright 基準測試。
2. 測試涵蓋 DM 與一般成員可見／可操作範圍、表單驗證、邀請操作回饋，以及權限敏感操作的確認流程；使用隔離測試帳號與資料。
3. 逐步遷移表單、按鈕、Tabs、Select、Dialog 和 Dropdown 等共用或複雜互動元件。
4. 對角色權限修改、轉移與刪除加強權限邊界驗證；UI 改造不得放寬任何既有伺服器端或資料庫權限。

**完成條件：** DM／玩家視角的主要情境均有對應 E2E 覆蓋；設定與權限操作行為保持不變；鍵盤可操作頁籤、選單與對話框。

### Phase 3：Campaign 背包頁

**範圍**

- Campaign 背包頁的公開／私人背包、道具展示與操作。
- 公開／私人錢包與貨幣操作。
- 排序、堆疊整理、道具建立／編輯、轉移及相關提示。
- 背包格子等產品專屬展示樣式；只抽取可明確共用的互動元件，不強制統一展示卡片。

**執行步驟**

1. 在開始遷移前，先建立背包頁 Playwright 基準測試，使用可重置的測試資料。
2. 覆蓋公開與私人權限下的可見性及操作能力、背包切換、搜尋／檢視模式、貨幣或物品操作的主要流程。
3. 優先遷移工具列、表單控制項、選單、提示與操作按鈕；保留背包格子、道具卡片等需要高度客製的視覺。
4. 驗證無權限資訊不會因 UI 重構而顯示；重量仍只計算使用者有權讀取的背包與錢包。
5. 在桌面與窄螢幕驗證公開／私人區分、道具操作和選單可用性。

**完成條件：** 背包主要流程和權限情境通過 E2E 測試；公開／私人資訊隔離、重量計算與貨幣／道具操作維持原有行為。

### 收尾：文件化與防止回退

1. 移除已遷移範圍內不再使用的重複 class 與舊元件。
2. 在共用元件附近記錄簡短用法，說明 variant、尺寸與語意。
3. 保持 E2E 測試以角色、標籤和可見文字等使用者可感知行為定位，不依賴 Tailwind class 或脆弱的 DOM 結構。
4. 將 E2E 測試納入專案日常驗證；若已有 CI pipeline，將 Playwright 測試加入 CI，並確保測試環境使用隔離資料。
5. 視維護成本再評估 Storybook、視覺回歸測試或更多表單抽象，不把它們列為本次必需條件。

**完成條件：** 三個 Phase 的 E2E 測試可穩定重複執行；共用元件有明確使用方式；客製化例外合理且可辨識。

## 驗收標準

- `npm run typecheck`、`npm run lint`、`npm run build` 通過。
- Playwright E2E 測試能在文件化的測試環境中重複執行，涵蓋 Phase 1、Phase 2、Phase 3 所列頁面的主要流程。
- 共用按鈕、輸入框和互動元件在主要狀態下視覺一致，且保留產品既有語意色。
- 可用鍵盤完成表單、頁籤、選單和對話框的主要操作；焦點可見，關閉對話框後焦點回到觸發元件。
- 窄螢幕沒有水平溢出、遮住主要控制項或無法操作的選單。
- 表單提交、權限限制、背包與貨幣操作、角色管理、Realtime 狀態同步與訪客／本機 fallback 的行為不變。
- 沒有為尚未採用的元件引入不必要套件，也沒有重複建置 Vaul 已提供的 Drawer 能力。
- E2E 測試不依賴真實 Email 寄送、真實玩家資料或不可控的外部服務。

## 風險與控制方式

| 風險 | 控制方式 |
| --- | --- |
| 元件庫預設風格沖淡產品辨識度 | 共用元件只提供互動基礎；以本專案語意 token 定義外觀 |
| 一次遷移造成大量回歸 | 每次只改一個頁面或功能區，通過驗收再繼續 |
| 表面重構意外改變業務邏輯 | UI 遷移不改資料流、權限、Supabase 呼叫與狀態同步 |
| 元件抽象過度，呼叫端 API 難懂 | 先從 Button、Input 等高重複元件開始；以真實頁面驗證 API |
| 引入套件與 Tailwind v4／React 19 不相容 | 在準備階段做小型相容性驗證，避免先大規模安裝 |
| 可見但不可鍵盤操作的自製選單 | 複雜互動採用成熟 primitives，並在驗收中檢查鍵盤行為 |

## 不在本次改造範圍

- 重設整體視覺品牌或全面翻新頁面版型。
- 修改 Supabase Schema、RLS、角色權限或資料同步架構。
- 重寫背包、重量計算、貨幣轉移或戰役管理業務邏輯。
- 強制將所有展示元件改為共用元件。
- 一次性導入完整元件庫或全站重新實作。

## 建議開始方式

先完成準備階段：盤點路由、引入 Playwright、建立測試資料策略，並為 Phase 1 建立改造前基準測試。接著建立 Button、Input 與表單提示等共用元件，再依 Phase 1、Phase 2、Phase 3 順序改造；每個 Phase 都先補足該範圍的 E2E 基準，再開始遷移，通過驗收後才進入下一階段。
